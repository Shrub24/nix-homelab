# Architecture

## Pattern Overview

**Overall:** Host-centric NixOS fleet infrastructure with modular service composition, provider-aware isolation, and blast-radius-secured secrets.

**Key Characteristics:**

- **Flake-driven:** `flake.nix` is generated by `flake-file` from the input declarations in the tree (`modules/flake/inputs.nix` for the shared baseline and the fleet-owned dependencies, or the contributor that owns a dependency); nix-fleet is the authority for the pins the repositories share. flake-parts discovery reaches every host contributor under `modules/hosts/<host>/`, and the generic host registry (`modules/flake/host-registry.nix`) materializes their typed `nixos.hosts.<id>` records into `nixosConfigurations` per host
- **Aspect composition:** Source ownership and deployment variability are independent axes. Normal feature source files are auto-discovered flake-parts contributors under their domain directory (`modules/<domain>/`) or, for materialization and fleet-baseline concerns, `modules/flake/`; several may merge into one `flake.modules.nixos.<aspect>` deployment aspect — `cache-publisher` consumes a shared nix-fleet mechanism through one contributor, while `ingress` remains composed from three (`modules/web/ingress.nix` plus its runtime and origin-exposure siblings). Host records select deployment aspects explicitly (selection is enablement) — the five foundation aspects `base`, `shell`, `networking`, `tailscale`, `notify`, the five operational aspects `state-backups`, `cache-publisher`, `builder-access`, `build-account`, `observability-agent`, the `dj`, `music`, and `kanidm-host-auth` deployment aspects, and the twenty-two placement aspects `oci`, `ingress`, `cockpit`, `push-server`, `identity-provider`, `termix`, `vaultwarden`, `homepage`, `gatus`, `beszel`, `webhook`, `paperless`, `postgres`, `ai-gateway`, `karakeep`, `niks3-cache`, `phoenix`, and `omniroute` (D-053, revised by D-054: `admin-hub` was removed and the former hub members are individual aspects; the former `internal-contracts` registry is retired, D-062). `provenance`, `oci-images`, `fleet-packages`, and `web-policy` are infrastructure support modules, not host-facing capabilities
- **Hosts are thin:** Host contributors (`modules/hosts/<host>/default.nix`) declare one typed host record — target system, Tailscale identity, the explicit aspect selection, and reimage facts — while the NixOS composition itself stays host-private in `_nixos.nix` and underscore-prefixed fragments
- **Shared capabilities are consumer-registered:** a capability that serves unrelated services exposes a typed registry those services contribute to, instead of holding a participant list. `services.state-backups.services.<name>`, `services.notify.events.<unit>`, and the PostgreSQL consumer registry (`services.postgres.consumers.<name>`, D-058) are the three instances of the pattern. Two of them separate the mechanism from a declaration-only surface every participant imports — `state-backups` renders the capture job in `modules/backups/state-backups.nix` while `modules/backups/state-backups/_consumer.nix` declares the registry and the capture settings, and PostgreSQL keeps the clusters in `modules/database/postgres.nix` with the declaration-only contract in `modules/database/postgres/_consumer.nix` — so a participant's registration evaluates on a host that does not run the mechanism. PostgreSQL additionally separates a host declares `services.postgres.instances.<name>` (port and data directory are host facts) and selects the `postgres` aspect, a consumer registers its database, credential, extensions, and setup SQL from its own module, and endpoint resolution prefers the host's own cluster (`services.postgres.localEndpoint`) before the internal contract
- **One shared capability deliberately has no registry:** the ClickHouse substrate (`services.clickhouse` in `modules/database/clickhouse.nix`, selected by the `clickhouse` aspect) owns only the server — enablement, package, `serverConfig`, the config restart trigger, the `/run/secrets/rendered` permission fix and the unit's restart policy — while each co-tenant contributes `environment.etc."clickhouse-server/users.d/<n>-<name>.xml"` and extends the unit's `restartTriggers` from its own module. ClickHouse merges that directory at startup, so a consumer needs no server-side provisioning and the registry would restate what the filesystem already expresses; a consumer asserts the substrate is selected by name, because an unselected substrate leaves it without a server rather than with a partial one. Ownership is a host decision, not a property of whichever consumer arrived first
- **Applications compose services:** Discovered concern owners (`modules/<domain>/<concern>.nix` plus private `modules/<domain>/_<concern>/` leaves) wire multi-service stacks behind one host-selected `flake.modules.nixos.<aspect>` toggle; the legacy `modules/applications/` evaluator-class root was deleted in Stage 7 (D-053)
- **Services own their internals:** Leaf service modules own enabling runtime config, `sops.secrets`, `sops.templates`, systemd units, and assertions
- **Provider isolation:** Cloud/platform quirks live in the host-selected `oci` aspect (`modules/oci/oci.nix`, which carries the provider body inline) — workload modules stay provider-agnostic; the legacy `modules/providers/` root was deleted in Stage 7 (D-053)
- **Policy-driven:** Fleet-wide defaults and web-service endpoint definitions in `policy/` are the single source of truth
- **Secret blast-radius:** `.sops.yaml` path-scoped rules limit decryption to only the hosts that need each secret

## Layers

**Flake Entrypoint (`flake.nix` + `modules/flake/`):**

- Purpose: Composes every flake output through flake-parts — host `nixosConfigurations`, devShell, packages, checks, deploy topology, and the `bootstrap.nodes` projection
- Location: `flake.nix` (generated by `flake-file`; input declarations in `modules/flake/inputs.nix` and `modules/flake/flake-file.nix`), flake-parts modules under `modules/flake/`
- Contains: The input declarations (`flake-file`, `nix-fleet`, the shared baseline as follows aliases to `nix-fleet/{nixpkgs,flake-parts,import-tree,sops-nix,niks3}`, and the fleet-owned `disko`, `deploy-rs`, `nix-index-database`, `traktor-m3u-sync`) and the generated `outputs` expression that discovers `modules/` through `denful/import-tree` without a filter. The import-tree boundary record was deleted with the transition (`core`/`profiles` left in Stage 2, `shared`/`storage` in Stage 5, `applications`/`providers` in Stage 7 D-053, `hosts` in Stage 8, `services` in the post-Stage-8 services-tree conversion): discovery is unfiltered, so a plain-NixOS module directory fails loudly instead of being filtered out, and the scaffold contract asserts the converted roots stay evacuated (D-060)
- Depends on: All submodules and library code
- Used by: `nix build`, `nixos-rebuild`, `deploy-rs`, CI workflows; `checks.<system>.check-flake-file` gates that the committed `flake.nix` matches the declarations

**Host Layer (`modules/hosts/`):**

- Purpose: One typed canonical host record per host plus the host-private NixOS composition it selects
- Location: `modules/hosts/<host>/default.nix` — a discovered flake-parts contributor declaring `nixos.hosts.<id>` (HIC-1/HIC-2)
- Contains: `default.nix` (the record: `system`, `tailscale.{hostname,tailnetSuffix}`, `composition.{extraModules,aspects,fragments}`, and reimage `bootstrap` metadata where applicable, which projects to `flake.bootstrap.nodes.<host>`), the private `_nixos.nix` composition, underscore-prefixed host fragments (`_disko-*.nix`, `_cockpit-auth.nix`, `_admin-runtime.nix`), and `facter.json` (kept un-prefixed because its path is a host-derivation input)
- Depends on: Published aspects (`flake.modules.nixos.<aspect>`) selected by the record, input-provided NixOS modules (`extraModules`), and concern-owned feature sources (aspects and their sibling contributors)
- Used by: `modules/flake/host-registry.nix`, which validates every record (named `host-registry:` errors for duplicate host IDs, malformed IDs, ID/key mismatches, duplicate Tailscale identities, and missing required fields) and materializes `flake.nixosConfigurations` through `inputs.nixpkgs.lib.nixosSystem`; `modules/flake/bootstrap.nix` projects `flake.bootstrap.nodes` from the same records

**Application Layer (former `modules/applications/`, deleted in dendritic Stage 7 / D-053):**

- Purpose: Composition roots that wire multiple interacting services behind one toggle; own shared paths and cross-service wiring, while concrete leaf mechanics live with their service owners
- Location: concern-owned contributors under their domain directory — `modules/music/music.nix` (dendritic Stage 6 / D-052) with the DJ contributor `modules/music/dj.nix` and its engine sibling `modules/music/dj-engine.nix`, `modules/identity/identity-provider.nix`, `modules/admin/cockpit.nix`, and the individual operator-tooling contributors `modules/admin/{termix,homepage,webhook}.nix` (the former `admin/` coordinator split, dissolved by D-054; the user-facing workloads then moved to their own domains), and `modules/web/ingress.nix` (former `edge-ingress.nix`). Stage 8 (D-056) moved these concern owners out of the flat `modules/flake/` bucket
- Contains: No `modules/applications/` root remains and no compatibility wrapper or underscore-renamed replacement root exists. Stacks whose mechanics belong to a service keep those leaves beside the concern owner (`paperless` has no application wrapper: the stack is composed directly from `modules/apps/paperless/{core,gpt}.nix`, and the music leaves live under `modules/music/**`)
- Depends on: Service modules, `policy/globals.nix`, `lib/secrets.nix`
- Used by: Host-record aspect selection only — hosts import no application implementation

**Service Leaf Layer (beside the owning concern):**

- Purpose: Leaf implementation modules for individual workloads — systemd services, Podman containers, runtime config
- Location: `modules/<domain>/<name>.nix` (a discovered aspect file or a sibling contributor of an existing aspect), with underscore-private helpers at `modules/<domain>/_<concern>/`
- Contains: Service enable flags, `sops.secrets` registrations, `sops.templates`, systemd units, assertions, restart semantics, multi-instance patterns (e.g., paperless-gpt with llm/docling OCR isolates)
- Depends on: `lib/secrets.nix`, runtime paths from the owning concern contributor
- Used by: flake-parts discovery, which publishes the file's own aspect, or the concern-owned contributor that imports it as a sibling; host records never import a workload service directly

**Deployment Aspect Layer (domain directories + `modules/flake/` for baseline and materialization):**

- Purpose: Cross-cutting host baseline published as selected deployment aspects — the five foundation aspects `base`, `shell`, `networking`, `tailscale`, `notify`, the five operational aspects `state-backups`, `cache-publisher`, `builder-access`, `build-account`, `observability-agent`, the `dj`, `music`, and `kanidm-host-auth` deployment aspects, and the twenty-six placement aspects `oci`, `ingress`, `cockpit`, `push-server`, `identity-provider`, `termix`, `vaultwarden`, `homepage`, `gatus`, `beszel`, `webhook`, `paperless`, `postgres`, `clickhouse`, `bifrost`, `karakeep`, `langfuse`, `latitude`, `niks3-cache`, `phoenix`, `omniroute`, `degoog`, `hindsight`, `docs-mcp`, `home-assistant` (D-053's placement surface, revised by D-054: `admin-hub` was removed with no replacement bundle and the former hub members are self-contained aspects; the observability store `victoria` joined in D-074). One aspect carries no capability at all: `container-env` is the fleet invariant that recreates a container whose environment file changed, so a new variable or a rotated secret reaches the running container (D-077). Selection is enablement: host registry records select the aspects they enable, selecting `dj` enables `applications.dj`, and selecting `dj` enables `applications.dj`, while the canonical OIDC contract is an intrinsic module imported by the modules that read it rather than a host-selected aspect (D-059). Aspect relationships are modeled by semantics — intrinsic composition (the owner directly imports a required implementation with no meaningful independent placement), policy co-selection (independently placeable capabilities selected together by host policy, optionally with a named assertion), and optional integration (activates only when both contracts are present; neither selects the other) — rather than a universal no-aspect-import rule
- Location: concern-owned contributors discovered under their domain directory (Stage 8 / D-056 relocation) — foundation `modules/flake/{shell,networking,tailscale}.nix` and the two-contributor `base` (`modules/flake/base.nix`, `modules/flake/base-host-recovery.nix`); notifications `modules/notifications/{notify,push-server}.nix`; operational `modules/backups/state-backups.nix` (with the declaration-only `modules/backups/state-backups/_consumer.nix`), `modules/cache/cache-publisher.nix`, and `modules/flake/{builder-access,observability-agent}.nix`; the invariant contributor `modules/containers/container-env.nix`; application/identity `modules/music/{music,dj}.nix` and the `kanidm-host-auth` capability (`modules/identity/kanidm-host-auth.nix`) and the intrinsic OIDC contract (`modules/identity/_oidc.nix`, imported by its readers rather than selected); placement `modules/oci/oci.nix`, `modules/web/ingress.nix`, `modules/admin/{cockpit,termix,homepage,webhook}.nix`, `modules/apps/{paperless,karakeep,vaultwarden,actual,memos,tududi,geopulse,homarr,inbox-zero}.nix` (paperless keeps its `paperless-gpt.nix` sibling) and `modules/apps/home-assistant.nix` (the upstream container, host-networked for discovery, with an operator-owned `/srv/data/home-assistant`; D-100), `modules/observability/{beszel,gatus,phoenix,langfuse}.nix`, `modules/knowledge/{degoog,hindsight,docs-mcp}.nix` (knowledge domain), `modules/identity/identity-provider.nix`, `modules/cache/niks3-cache.nix`, `modules/database/postgres.nix`, `modules/database/clickhouse.nix`, and `modules/web/web-policy.nix`. A second contributor joins a concern by publishing the same aspect name from a sibling file (`modules/flake/base-host-recovery.nix`, `modules/music/{dj-engine,windows-vm}.nix`, `modules/web/ingress.nix`); five of those contributors consume a shared nix-fleet mechanism and supply only the fleet's conventions — `modules/flake/tailscale.nix`, `modules/flake/builder-access.nix`, `modules/flake/observability-agent.nix` (the shared `beszel-agent` module), `modules/cache/niks3-cache.nix` and `modules/cache/cache-publisher.nix` (D-061). `_` is reserved for a value-imported helper, declaration-only contract, or data directory beside its owner (`modules/flake/shell/p10k.zsh`, `modules/music/_beets/runners.nix`, `modules/admin/homepage/_data.nix`, `modules/backups/state-backups/_consumer.nix`, `modules/identity/_oidc.nix`, `modules/identity/_kanidm-packages.nix`)
- Contains: `base` (policy, users, host-recovery import, and the typed `fleet.foundation.bootLoader` / `fleet.foundation.buildTmpfsSize` host facts), `shell` (zsh/p10k, wezterm, nix-index comma), `networking` (native networkd contract rendered from `fleet.networking` facts), `tailscale` (the shared nix-fleet mechanism plus the conventional host-scoped auth-key binding), `notify` (the shared notification mechanism: daemon, CLI and event-handler packages), `state-backups`/`cache-publisher`/`builder-access`/`observability-agent` (operational capabilities, D-049; the combined `backups` aspect was split by D-055; `cache-publisher` and `observability-agent` consume shared nix-fleet mechanisms, while `builder-access` projects trust from nix-fleet's canonical fleet inventory and `build-account` is the inbound half of the same contract (D-061/D-066/D-068, D-082), the invariant `container-env` (an all-host unit revision derived from each container's environment file, D-077), `dj` (application enablement, D-050), `kanidm-host-auth` (the Kanidm Unix/PAM/SSH capability; D-051, renamed and de-bundled by D-059 — the OIDC contract moved to the intrinsic `modules/identity/_oidc.nix`), the telemetry lanes `telemetry`/`telemetry-metrics`/`telemetry-logs`/`telemetry-otlp` over nix-fleet's contract and its signal lanes (D-083), with the AI route's per-destination output views declared in the OTLP lane's collector policy (D-084) and the adopted host-observability producers — the systemd unit-state collector on the exporter, the Tailscale scrape source every metrics-selected host realizes, and the identity join to the canonical host IDs, all values of nix-fleet's contract rather than local contributions (D-085) — and the Stage 7 and decoupling placement aspects — `oci` (provider boot/serial console), `edge` (edge/origin proxy plus the guarded policy projection), `cockpit`, `push-server` (LA ntfy), `identity-provider` (sole owner of Kanidm runtime/provisioning and the OIDC provisioning secret-source map), the individual admin workload aspects `termix`, `vaultwarden`, `homepage`, `gatus`, `beszel`, and `webhook` (each with its own enablement, runtime, and secret contracts), `victoria` (the observability store: VictoriaMetrics, VictoriaLogs and VictoriaTraces with their Grafana front end, every port read from its web-policy declaration, D-074), and the OCI/home-forge workloads `paperless`, `postgres`, `clickhouse` (the observability backends' shared server: ownership of the server is its own decision, and each co-tenant contributes only a `users.d` fragment, D-111), `bifrost`, `karakeep`, `langfuse`, `latitude`, `niks3-cache`, `phoenix`, `omniroute`, `degoog`, `hindsight`, `docs-mcp` (D-053, revised by D-054; `bifrost` became a native nix-fleet build, D-078, and the mechanism moved to a nix-fleet aspect, D-079), plus the knowledge-domain workloads — `degoog` (private search front end; pinned upstream module with a sibling contributor owning its settings environment, private-instance posture, and `/var/lib/degoog` backup), `hindsight` (agent memory; digest-pinned container, PostgreSQL consumer registration with pgvector, model-cache bind excluded from live-state backup), and `docs-mcp` (grounded documentation index; digest-pinned container with explicit `DOCS_MCP_PROTOCOL=http`, store/config under `/srv/data/docs-mcp`, `sqlite3 .backup` export in the backup contract) — and `langfuse` (the LLM observability stack on home-forge) with `latitude` (the agent-failure triage console trialed beside it, D-071: the PostgreSQL substrate with pgvector, native ClickHouse in its own database and its own `users.d` fragment, two native Redis instances for the cache and the append-only BullMQ queue, Temporal plus six digest-pinned application containers, object storage on `/srv/storage/latitude`, OTLP/HTTP ingest with no ingress route, and a UI route that Access gates while the API origin stays Access-free because the browser calls it directly). Aspect selection is independent: `la-admin-1` selects the capabilities it wants, no aspect owns or configures a sibling, and real cross-aspect dependencies fail through named contract assertions rather than missing-option errors. An aspect may import its own helper or sibling contributor — e.g. `modules/flake/tailscale.nix`, `modules/notifications/notify.nix`, `modules/flake/base-host-recovery.nix`, `modules/music/dj-engine.nix`, `modules/web/ingress.nix`, and the OCI provider body nested in `modules/oci/oci.nix` — without creating a public dependency
- Depends on: Its own sibling contributors and underscore-private helpers under the same domain directory, plus `policy/`

**Infrastructure Support Modules (`modules/flake/{provenance,fleet-packages}.nix` plus the domain-owned `modules/containers/oci-images.nix` and `modules/web/web-policy.nix`):**

- Purpose: Typed repository data, package projections, provenance, and resolved web policy for lower-level consumers — infrastructure wiring, not host-facing deployment capabilities
- Location: concern-owned contributors under `modules/flake/`
- Contains: `provenance` (source provenance), `oci-images` (typed OCI image policy data), `fleet-packages` (per-system package projection), `web-policy` (resolved `repo.web` hosts/catalog/currentHost from `policy/web-services.nix`; selected on every host because the notification defaults and host policy consume it, D-051)
- Retirement: each support module disappears as its consumers migrate to native projections (feature-owned lexical capture, intrinsic registry/base composition, feature contributors injecting their own packages)

The former `modules/core/` and `modules/profiles/` directories were deleted in dendritic Stage 2 (`dendritic-stage-2-foundation-aspects`); their behavior became the foundation aspects above or the operational aspects and feature leaves selected in host records. Dendritic Stage 3 (`dendritic-stage-3-operational-aspects`) converted the five deferred operational leaves into the `backups`, `builder-access`, and `observability-agent` aspects (see `docs/decisions.md` D-049): `backups` composes state backups, the niks3 upload client, and post-deploy closure upload; `builder-access` owns remote-builder SSH trust over nix-fleet's canonical fleet inventory (D-065, revised by D-066); `observability-agent` owns Beszel agent enrollment. Dendritic Stage 4 (`dendritic-stage-4-source-model-realignment`, D-050) replaced the central `modules/flake/aspects.nix` with concern-owned discovered contributors, classified `provenance`/`oci-images`/`fleet-packages` as infrastructure support, made `dj` selection enable `applications.dj`, and reframed plain class-oriented leaves and the filter as transitional (see `docs/decisions.md` D-050). Dendritic Stage 5 (`dendritic-stage-5-shared-source-contributors`, D-051) deleted the `shared`/`storage` roots, relocated the private leaves to `_aspects`/`_backups`/`_builder-access`, promoted `web-policy` to the all-host support quartet, merged the two identity contributors into `identity-client`, and shrank the filter from six entries to four (D-059 later retired that bundle: the OIDC contract is the intrinsic `modules/identity/_oidc.nix` and the capability is `kanidm-host-auth`). Dendritic Stage 7 (`dendritic-stage-7-placement-aspects`, D-053) converted every remaining deployed product/platform capability into a discovered placement aspect, relocated the admin/edge/DJ/OCI implementations beside their concern owners, deleted `modules/applications/` and `modules/providers/`, and shrank the filter to exactly `hosts` and `services`. Dendritic Stage 8 (`dendritic-stage-8-host-identity-contracts`, D-056) made host identity canonical and discovered: every host declares a typed `nixos.hosts.<id>` record from its own contributor, the concrete `nixos.configurations` table and the transitional loader were deleted, `modules/flake/bootstrap.nix` was reduced to the `flake.bootstrap.nodes` projection, deploy and web metadata gained fail-closed canonical-host-ID validation, the tailnet suffix gained a single authority, the two internal transport contracts were added under `modules/fleet/` (since retired in favour of the policy's private-endpoint projection), and the settled concern contributors moved into domain directories. The OCI cache server (`modules/cache/niks3-cache.nix`) is a leaf owned by the `niks3-cache` aspect. The post-Stage-8 services-tree conversion then converted the remaining service leaves into discovered contributors — each became its own aspect file, a sibling contributor of its owner aspect, or an underscore-private helper beside that owner — and emptied the import-tree exclusion.

**Policy Layer (`policy/`):**

- Purpose: Canonical fleet-wide non-secret defaults and web service endpoint definitions
- Location: `policy/`
- Contains: `globals.nix` (S3, Nix substituters, AI gateway, application defaults, and the single `tailnet.suffix` authority read by both the host records and the web policy), `web-services.nix` (SSOT for endpoint routing: plain data taking nix-fleet's canonical service records, so a canonical route's `origin` derives from the service inventory while `origin.provider` placements are validated against canonical host records), `identity.json`, `bifrost-config.json`

**Library Layer (`lib/`):**

- Purpose: Reusable Nix helpers for secrets, deploy wiring, and policy resolution
- Location: `lib/`
- Contains: `secrets.nix` (secret option helpers), `deploy/default.nix` (deploy-rs node wiring), `deploy/hosts.nix` (host metadata), `policy.nix` (web policy resolution and Cloudflare export)

**Secrets Layer (`secrets/`):**

- Purpose: SOPS-encrypted values scoped by blast radius with explicit `.sops.yaml` rules
- Location: `secrets/`
- Contains: Host-scoped (`secrets/hosts/<host>/system.yaml`, `oidc.yaml`), application-scoped (`secrets/applications/<name>.yaml`), service-scoped (`secrets/services/<name>.yaml`), fleet-shared (`secrets/common.yaml`), identity secrets, OpenTofu secrets, templates
- Depends on: `.sops.yaml` recipient policy, `sops-nix` activation-time decryption
- Used by: Host, application, and service modules

**Notification Layer (`modules/notifications/` + nix-fleet):**

- Purpose: HTTP notification dispatch with dual-channel delivery (Telegram via apprise, UnifiedPush via ntfy), plus the `notify` CLI and native systemd event notification. ntfy is the fleet's live push path; the Telegram channel is bound but switched off by policy (`services.notify.telegram.enable = false`, D-068). The daemon publishes to the catalog's ntfy `endpoint` — loopback on the host that serves ntfy, the provider's tailnet name elsewhere — so a publish never crosses the public edge (D-073)
- Location: `modules/notifications/notify.nix` (the `notify` aspect convention contributor); the mechanism — daemon, CLI, `unit-notify` handler and the `services.notify.events` registration contract — is owned by nix-fleet's `notify` aspect
- Contains: the fleet's notification policy (Telegram chat/topic map from `policy/globals.nix`, the ntfy server URL derived from the web catalog, the conventional host-scoped secret files) and the fail-closed secret bootstrap; upstream renders the `notification-daemon` FastAPI app (`/health`, `/notify`, `/debug/test-notify`), the `notify` CLI wrapper that POSTs to the daemon, and the native OnFailure/OnSuccess handler

**CI/CD Layer (`.github/workflows/`):**

- Purpose: GitHub Actions automation for validation and deployment
- Location: `.github/workflows/`
- Contains: `ci.yml` (validation only: formatting, the repository's contract tests and the generated `flake.nix` freshness comparator; callable, so the build workflow reuses it), `fleet-build.yml` (the fleet build plane: hand-dispatched on `main`, validation first, calling nix-fleet's reusable `build-push-cache` workflow on `.#checks`), `package-updates-refresh.yml` (weekly refresh of the registered package pins, evaluated, opening one pull request), `deploy.yml` (manual full deploy pipeline with serial ordering), `deploy-host.yml` (reusable host deploy: verifies the profile is substitutable, then activates)
- Depends on: nix-fleet's builder contract (build-account, the `ci` profile and its reusable workflow), the fleet niks3 cache, Tailscale GitHub Action for tailnet access
- Used by: Repository automation

## Data Flow

**Host Bootstrap Flow:**

Host initialization is conditional on target state — see `docs/runbooks/host-initialization.md`:

1. **Adoption** (existing preinstalled NixOS on a live disk): consume a committed `nixos-facter` report directly (`hardware.facter.reportPath`) with only root/ESP by-UUID mounts hand-maintained, then apply the first generation with `nixos-rebuild boot --target-host <initial-user>@<addr> --use-remote-sudo --flake .#<host>` and reboot from the provider console. No reimage tooling is involved.
2. **Reimage** (bare, foreign OS, or destructive layout): `just bootstrap` sources `scripts/resolve-host-config.sh`, which resolves the typed `flake.bootstrap.nodes.<host>` projection (bootstrap metadata owned by the host's `nixos.hosts.<id>` record; `hostName` and `flake` derived from the record key by `modules/flake/bootstrap.nix`) and passes it to `deploy.sh`; `nixos-anywhere` runs over SSH with `--flake` target and `disko` partitioning — `deploy.sh`
3. Host installs with base config, no host-scoped secrets yet (two-step bootstrap default)
4. Post-install: retrieve SSH host key, derive age recipient via `ssh-to-age` — `just host-age <host>`
5. Add age recipient to `.sops.yaml`, re-encrypt host secrets, deploy — operator workflow

**Deployment Flow:**

1. Operator runs `just deploy <host>` — main `justfile`
2. `deploy-rs` reads host metadata from `lib/deploy/hosts.nix` — `lib/deploy/default.nix`; `modules/flake/deploy.nix` first validates every node key, `edgeHost`, and `deployOrder` entry against the declared canonical host IDs and fails closed with a named `deploy: unknown host reference …` error
3. `deploy-rs` builds the host profile and activates over SSH with rollback protection
4. Post-deploy hook sends `notify info` on success or `notify warning` on failure — `justfile` deploy recipe with inline notification
5. CI deploys follow the same pattern — the profile is verified substitutable (`max-jobs 0`, no builders) before activation — with `--remote-build` and serial ordering (`la-admin-1` → `oci-melb-1`)

**Secret Resolution Flow:**

1. Host config binds secret file paths (e.g., `applications.music.secretFiles.host`)
2. Application/service module registers `sops.secrets` entries referencing that file
3. `sops-nix` decrypts at activation time — secrets are plaintext only during runtime
4. `sops.templates` render config files with secret placeholders replaced
5. `.sops.yaml` path-scoped rules control which age recipients can decrypt each file

**Web Service Routing Flow:**

1. `policy/web-services.nix` defines services with subdomain, `origin { scheme, provider, port }` placement, exposure mode (plain data; `origin.provider` names a canonical host ID — dial addresses are derived at the consumer, never declared)
2. `modules/web/web-policy.nix` validates the policy before resolution — unknown host keys, origins whose `origin.provider` is not a declared canonical host ID, and a `direct` route whose provider is not the policy host fail closed with named `web-policy:` errors
3. `lib/policy.nix` resolves host services — `resolveHostServices` merges defaults
4. the discovered `ingress` aspect (`modules/web/ingress.nix` + `modules/web/ingress-runtime.nix` + `modules/web/ingress-origin-exposure.nix`, over the shared route projection in `modules/web/_ingress-routes.nix`) enables the Caddy reverse proxy with role-based configuration (edge/origin/none) — selected by `oci-melb-1` (edge, the `edgeHost` topology fact) and `la-admin-1` (origin), with routes projected from this policy for the edge role only. A host that serves an origin additionally renders the front for every private-transport route it provides, from `repo.web.originServices`
5. `lib/policy.nix` exports Cloudflare DNS configuration via `resolveCloudflareHosts` — the exported policy is generated for the edge host (`edgeHost` in `lib/deploy/hosts.nix`), and the policy's host key names the ingress host, not the workload host
6. `scripts/export-web-services-policy.sh` generates JSON for OpenTofu consumption
7. OpenTofu manages Cloudflare DNS records and Access policies — `access.requireCloudflareAccess` (on by default) is enforced twice: the Access application at Cloudflare's edge, and a Caddy matcher at the origin that answers 403 to any request lacking the Access identity header. In-fleet machine clients (SDK/OTLP exporters, API callers) therefore reach such a route through the provider's tailnet-direct origin on the declared port, never the public hostname; a route whose clients cannot traverse the edge gate (Bitwarden/Navidrome/Subsonic clients, ntfy publishers, the Kanidm provider itself) opts out with `requireCloudflareAccess = false`. `access.oidc.enabled` is a separate axis — the consumer switch that turns an application's own OIDC login on — so the two are set independently

**Media Ingest Flow:**

1. `slskd` downloads to `/srv/storage/media/music/inbox/slskd`; each `DownloadDirectoryComplete` event restarts `slskd-settle.timer` (scoped polkit grant for the `slskd` user), which starts the pipeline 60s after the last event
2. `dropbox` path watcher (`systemd.paths.dropbox-inbox`, target declared via `pathConfig.Unit`) triggers on new files
3. `ffmpeg-preprocess.service` converts lossless to AIFF; timer persistence provides boot catch-up for unprocessed inbox media
4. `beets-inbox.service` imports preprocessed files into library
5. Completed files moved to `/srv/storage/media/music/library`, quarantined files to `/srv/storage/media/music/quarantine`
6. SoulSync provides control-plane ingest with Discogs-first metadata
7. Operator invokes `beets-quarantine-interactive` for manual quarantine review
8. Syncthing syncs library and quarantine to connected devices
9. Runner failures notify via `notify` CLI to the notification daemon — `beets-notify-failure@` systemd template unit

**Notification Dispatch Flow:**

1. Caller sends notification via `notify` CLI (`echo "msg" | notify send <severity> [title] [--topic <topic>]`) or HTTP POST to `http://127.0.0.1:5555/notify`
2. Notification daemon dual-dispatches via apprise (Telegram with topic routing) AND ntfy (UnifiedPush with per-topic channels)
3. A registered unit fires the notify aspect's native `OnFailure=`/`OnSuccess=` handler (`notify-event@<unit>.service`), which reads the rendered policy map at `/etc/notify/events.json` and POSTs the outcome with journal context to the notification daemon
4. Deploy notifications (`just deploy`) use `notify info/warning` inline in the justfile recipe

**Paperless Document Management Flow:**

1. `services.paperless.enable` toggles the Paperless document management stack
2. Paperless core (`modules/apps/paperless.nix`) runs the Django-based document management system with OIDC authentication via Kanidm
3. Paperless-GPT (`modules/apps/paperless-gpt.nix`) provides AI document enhancement with a docling-serve sidecar for OCR and document analysis (imported as a submodule of `services.paperless`; the host file configures it directly via `services.paperless.paperless-gpt` with per-instance enables (`instances.llm.enable`, `instances.docling.enable`) and the shared sidecar toggle (`docling.enable`))
4. Both services connect through the shared PostgreSQL mechanism (`modules/database/postgres.nix`, D-058) with niks3-managed backup
5. Post-consume hook triggers a notification via the notification daemon on new document ingestion

**Bifrost AI Gateway Flow:**

1. Selecting the `bifrost` aspect deploys the gateway: the aspect imports nix-fleet's `flake.modules.nixos.bifrost`, so there is no enable flag (D-079)
2. The fleet module runs the dynamically linked build as a native service (`-app-dir`, `-host`, `-port`) under a dedicated account, with only its application directory writable, and installs `config.json` from the Nix store before every start — the repo-owned `policy/bifrost-config.json` plus the two registrations under `services.bifrost.plugins`
3. Providers are declared in `policy/bifrost-config.json` (Gemini, DeepSeek, `opencode-go` as a two-key pool, OpenRouter, and Voyage as a custom provider) and model aliases resolve through governance routing rules; `source_of_truth: "config.json"` makes that file, not the UI, the authority for providers and rules (D-076), while the admin account is declared as `auth_config` with env indirection because the runtime no longer reads admin credentials from the environment
4. The `voyage-normalizer` plugin strips the `encoding_format: "float"` field Voyage rejects with a 400 and maps `dimensions` to `output_dimension` — the only place docs-mcp's hardcoded field can be repaired once for every consumer (D-078)

**Documentation Index Flow (docs-mcp):**

2. Embedding requests go to the host-supplied gateway origin with the fleet embedding alias; the gateway authenticates no client, so the module passes the same placeholder credential its other consumers use

**Observability Store Flow (victoria):**

1. Selecting the `victoria` aspect on home-forge enables the three native store services and Grafana; every listener port closes over its web-policy declaration (D-074)
2. Producers compose the telemetry lanes for the signals they ship — `telemetry-metrics` (vmagent scraping the loopback node exporter from the `node-exporter` aspect — which also collects systemd unit state — plus the Tailscale daemon's own endpoint on the tailnet-local address, remote-written to the store), `telemetry-logs` (Vector shipping journald to VictoriaLogs, normalizing well-formed trace and span identifiers so a record joins its trace), and, where an instrumented producer exists, `telemetry-otlp` — over the bare `telemetry` contract, which is vocabulary plus this repository's fleet policy and starts nothing itself. `home-forge` is the fleet gateway for OTLP signals. Both its general ingress and its independently addressed `ai` route admit traces, metrics and logs: the general route sends each to its operational store, while the AI route additionally sends traces to Langfuse and Latitude (D-083). The route marker `telemetry.route="ai"` is fixed resource provenance applied only on AI branches; it is not classification or access control. The routing split is not an admission guarantee — a tailnet peer able to reach the listener can publish to all destinations selected by that route. OTLP logs on both routes are default-deny: only resource `host.name`, `service.name`, `deployment.environment.name` and, on the AI route, `telemetry.route` survive, while body, timestamps, severity and trace correlation fields remain intact; journald continues through Vector. Trace output views still shape the same route receiver per destination: Langfuse receives spans with vendor keys mapped from their canonical carriers and duplicates pruned (D-088), Latitude's leg bridges the deployed image's legacy message format, and VictoriaTraces receives spans with message carriers and content-bearing events removed (D-084, D-086)
3. Grafana serves read-only anonymous viewers behind Cloudflare Access, with its whole reader surface provisioned from Nix: four datasources (a prometheus-typed `victoriametrics` as the default, the MetricsQL plugin datasource, the logs plugin datasource, and the built-in Jaeger datasource against VictoriaTraces' Jaeger-compatible API), four plugins, and seven dashboards in three folders (`Fleet`, `Host`, `Telemetry`): four upstream boards rewritten on the way in, the Tailscale Machine board (grafana.com 24178, relabelled from the tailscale-mixin's `cluster`/`tailscale_machine` dimensions to the fleet's `host` label), and two boards authored in `modules/observability/dashboards/` (`fleet-overview`, and `pipeline-health` for Vector, OpenTelemetry Collector and vmagent health). The community Vector stats board (grafana.com 15105) is not imported: its queries use an older Vector metric schema (`vector_processed_events_total`, `component_name`) that the store does not carry. Every board addresses the board's own datasource — upstream boards hardcode a uid and mark panels `prometheus` regardless of the store behind them. Datasource uids are declared once in the module; changing one requires clearing Grafana's provisioned state before activation, because provisioning resolves a datasource by uid and fails the whole module graph when the stored row does not carry it
4. Retention is the volume control, on the placing host's root filesystem; the telemetry contract owns the producer seam, and every destination URL derives from the store's catalog entries, so repointing a backend is one contributor edit

## Key Abstractions

**Host Identity:**

- Purpose: Declares the canonical host record — stable host ID, target system, Tailscale identity, deferred NixOS composition, and reimage facts
- Location: `modules/hosts/<host>/default.nix` (the record) validated and materialized by `modules/flake/host-registry.nix`; physical deploy facts stay in `lib/deploy/hosts.nix`
- Pattern: One discovered contributor per host publishing `nixos.hosts.<id>`; identity is declared once and referenced (never restated) by deploy metadata and web policy, which both fail closed on unknown host IDs

**Private Service Endpoints:**

- Purpose: cross-host private transports without restating a provider host name, and without a second topology abstraction beside the web policy
- Location: the resolved catalog from `policy/web-services.nix` (`modules/web/web-policy.nix` + `lib/policy.nix`)
- Pattern: every service in the policy is either published or private, and every catalog entry carries the published upstream *shape* (scheme + port) plus a machine-to-machine `endpoint { scheme, host, port, url }` — loopback when the evaluating host serves the service, the provider's tailnet name otherwise. A published service additionally exposes its public identity and never a public dial address; a private service (declared `tailscale-only` + `declarePublic = false`) leaves `publicUrl`/`publicHost` null. In-fleet clients dial the endpoint, never the public hostname, so a publish or API call never crosses the edge's Access gate (D-073). The declaration is the single source for both sides: the provider's listen port and every consumer's target URL derive from the same entry, so the port cannot drift. Placement is identity, not address: routes declare `origin.provider` (a canonical host ID) and each consumer derives its own dial by one of two policies over that fact — the ingress upstream from the route's `exposureMode` (`direct` loops back edge-locally and is validated as such; every tailnet mode dials the provider's FQDN even when provider and edge coincide, because its socket belongs to the tailnet), the private `endpoint` against the evaluating host (loopback when colocated with the provider, so a provider move is one policy edit) — while identity fields (public URLs, OIDC endpoints, TLS server names) stay literal and stable (D-063, D-064). The edge stays the one consumer of the full `repo.web.hosts` resolution, which carries placements and their derived dials. A route whose provider socket is not directly reachable declares `exposureMode = "tailscale-serve"`; the provider host receives that route through `repo.web.originServices`, renders its own front on the declared port, and the edge dials the provider's canonical private name with public-root verification (D-063). That front terminates TLS itself, so the dial is `https` whatever scheme the application speaks — `dialScheme` in `lib/policy.nix` decides it once for both the edge upstream and the catalog endpoint, because dialing the front at the app's own scheme is a plain-HTTP request to a TLS listener. A route may also have no socket at all: an apex `redirectTo` route is answered by the edge with a permanent redirect, carries no origin, and is absent from the cross-host catalog (D-106). A service that can run on more than one host publishes a second, aspect-owned fact beside the catalog — `services.<name>.localEndpoint`, the loopback listener that host binds — because a catalog dial keys on the declared provider and cannot know a second instance exists. A co-located consumer prefers it and falls back to the catalog, so placement and local consumption stay separate decisions (D-087).

**Service Address (container → native service):**

- Purpose: a stable address a container can dial to reach a native service on the same host, without depending on a Podman bridge gateway — which exists only while a container attaches to that network, and arrives as untrusted ingress
- Location: `policy/globals.nix` `serviceNetwork` (interface `svc0`, `10.255.0.1/32`, container-facing name `host.services.internal`), rendered by the `networking` aspect; a service opens one destination-matched rule through `lib/networking.nix` `mkServiceIngressRule`
- Pattern: native services bind loopback plus the service address; containers dial the name from their own per-app bridge. Peer containers stay on their bridges — this address is only for the host. A dialer in the host network namespace arrives as the service address itself, so its service-side ACL (`pg_hba` CIDRs, ClickHouse `networks`) lists the address, while a bridged dialer arrives as its bridge address; a stack whose containers mix both namespaces dials the address and allows both

**Canonical Fleet Inventory (nix-fleet) and Its Projections:**

- Purpose: one declaration of who the fleet's machines are and what build capacity each contributes, for both host-to-host trust and CI
- Location: nix-fleet's `modules/fleet/inventory.nix` — `fleet.hosts` (system, Tailscale hostname, host names, host public key, management user, `capabilities.nixBuilder`), `fleet.externalBuilders`, `fleet.buildProfiles` — with the typed schema, the fail-closed validation, the render check and the CI bundles beside it (`modules/fleet/{schema,feature}.nix`), and the pure projections published as `flake.lib.buildProfile`. This repository declares none of it (D-066): each host contributor only derives `system` and `tailscale.hostname` from `config.fleet.hosts.<id>` into its own record, and `modules/flake/builder-access.nix` projects trust from the merged fleet config (D-068), with `modules/flake/build-account.nix` binding the canonical CI coordinator key as the account's only authorized key (D-082); ssh-ng also requires that name in `nix.settings.trusted-users`, an effectively root-level Nix privilege owned by the selected upstream aspect, now pinned at `a48a1dcf`. Host activation remains pending; do not duplicate the binding locally
- Pattern: a canonical fact is declared once, upstream, and derived here — the host registry fails closed with a named error when a record has no canonical counterpart (the join-key rule). nix-fleet publishes facts and pure projections, never a NixOS module (v2 deleted the cross-class realization): the contributor imports the feature, closes over **this** evaluation's `config.fleet`, and renders trust for the hosts that offer build capability. Scheduling is off — no profile is resolved, so no host gets `nix.buildMachines` — because CI is the build path and coordinates builders by architecture: the hosts accept CI's build jobs through the `build-account` aspect, and the profile's rendered machines file belongs to CI rather than to a host daemon (D-082). Each host's `publicKey` binds in nix-fleet's inventory.
- Service endpoints: nix-fleet's service inventory (`lib/service-inventory.nix`; contract `docs/contracts/services.md`) declares each cross-fleet endpoint's host, scheme, port and base path, published as `lib.serviceEndpoints.canonicalServices` for plain-data policy and `resolveEndpoint config.fleet` for flake-level code. The web policy derives a canonical route's whole origin from it and the provider modules close over the resolved port, so local policy keeps only exposure, access and health (D-072).

**Application Stack:**

- Purpose: Multi-service feature composition with shared paths, secrets, and tmpfiles
- Location: `modules/<domain>/<concern>.nix`, publishing `flake.modules.nixos.<aspect>`, with a sibling contributor or underscore-private helper beside the owner under `modules/<domain>/`
- Pattern: Selection supplies the application's enable flag; the host keeps dataRoot + secretFiles passthrough only; the contributor imports sub-services, defines shared paths, and uses `lib.mkMerge` for conditional composition

**Ingress:**

- Purpose: Host-level reverse proxy composition with role-based configuration
- Location: `modules/web/ingress.nix` (the discovered aspect and policy projection) + `modules/web/ingress-runtime.nix` (the Caddy runtime, ACME credentials and secret contract) + `modules/web/ingress-origin-exposure.nix` (the provider-side front for private-transport routes)
- Pattern: Selection supplies `services.ingress.enable`; the host keeps only `role` (edge/origin/none) and its application-scoped secret binding; the runtime owns the service namespace, so no intermediate application layer restates its fields. The origin-exposure sibling owns every transport-specific detail, so a service module never learns how the private network exposes it

**Paperless Service:**

- Purpose: Document management stack with Paperless core, OIDC auth, and optional AI enhancement
- Location: `modules/apps/paperless.nix` (imports the `gpt.nix` submodule)
- Pattern: Enable flag + dataRoot + two secret files (host/oidc); `services.paperless.paperless-gpt` configured directly by the host, with multi-instance enables (`instances.llm.enable`, `instances.docling.enable`) and a shared docling sidecar toggle (`docling.enable`); seeds Django groups for OIDC sync

**Bifrost Gateway Service:**

- Purpose: OpenAI-compatible model gateway holding the fleet's provider inventory and routing rules, with an admin-authenticated dashboard and one native request-filter plugin
- Location: `modules/ai/bifrost.nix` (the aspect: imports nix-fleet's gateway service and supplies the canonical port and carries this repository's policy)
- Pattern: Aspect selection is deployment, and only policy stays here — the provider and routing document as `services.bifrost.settings`, the plugin registrations (`otel`, and the native `voyage-normalizer` from `repo.packages.bifrost-voyage-plugin`), the SOPS-rendered environment file, the container-facing ingress rule, the backup registration, and the secret file as a second restart trigger. The fleet owns the package, the service account, the application directory, the startup-configuration install and the failure notification; `policy/bifrost-config.json` stays the file authority for providers and routing rules

**Service Module:**

- Purpose: Single workload with enable flag, runtime config, secrets, and systemd integration
- Location: `modules/<domain>/<name>.nix`
- Pattern: Options → config with `lib.mkIf`, explicit `secretFiles.*` contract inputs, `sops.secrets` ownership internal to the module

**Secrets Contract:**

- Purpose: Typed option inputs for secret file paths with required assertions
- Location: `lib/secrets.nix`
- Pattern: `mkSecretFileOption`, `mkSecretKeyOption`, `mkRequiredSecretAssertion`, `mkSecretsFromMap`

**Web Policy SSOT:**

- Purpose: Declarative endpoint definitions consumed by Caddy, Cloudflare, and OpenTofu
- Location: `policy/web-services.nix` (data), `modules/web/web-policy.nix` (canonical-host validation + resolution into `repo.web`), `lib/policy.nix` (resolver)
- Pattern: Defaults + host service map → host-ID/FQDN validation against the canonical records → resolved by `lib/policy.nix` → exported as JSON for OpenTofu

**Disko Storage Layout:**

- Purpose: Declarative partition, filesystem, and mount point definitions
- Location: `modules/hosts/<host>/_disko-*.nix` (host-local, underscore-private)
- Pattern: `disko.devices.disk.main` with GPT layout, ext4 filesystems, labeled partitions

**Notify CLI:**

- Purpose: Python CLI wrapper that POSTs notification payloads to the daemon
- Location: `pkgs/notify/default.nix`
- Pattern: Reads stdin as message body, accepts positional args (tier, title, type, topic), POSTs to `NOTIFY_URL` (default `http://127.0.0.1:5555/notify`)

**Systemd Event Notification:**

- Purpose: Automated notification for systemd unit outcomes, registered by the capability that owns each unit
- Location: the registration `services.notify.events.<unit>` is written by the owning module; the handler unit, the policy map and the hooks are rendered by nix-fleet's `notify` aspect
- Pattern: native `OnFailure=` — and `OnSuccess=` only for units whose clean stop is a semantic event — attaching `notify-event@<unit>.service`, merged additively so owner-defined hooks survive

**Notification Daemon (nix-fleet `pkgs/notification-daemon/`):**

- Location: nix-fleet `pkgs/notification-daemon/notification_api/main.py`, deployed through the shared `notify` aspect

## Error Handling

**Strategy:** Fail closed at evaluation time — assertions (`lib.mkRequiredSecretAssertion`) prevent activation when required secret files are missing. `sops-nix` handles decryption failures at activation time. Systemd services use `Restart=on-failure` for runtime recovery. `deploy-rs` provides built-in rollback on activation failure. Pre-deploy checks (`just checks all`) run flake validation, secret scope checks, and web policy contract validation before any deployment.

## Cross-Cutting Concerns

**Logging:** NixOS `services.journald` with 300M max use, 7-day retention. Service-specific logging via `journalctl -u <unit>`. Notification daemon uses Python `logging` module.

**Observability:** `home-forge` runs the fleet's metrics/logs/traces store (`victoria` aspect: VictoriaMetrics + VictoriaLogs + VictoriaTraces) with Grafana published behind Cloudflare Access. Producers compose nix-fleet's telemetry lanes per signal — `telemetry-metrics`, `telemetry-logs`, and `telemetry-otlp` where an instrumented producer exists — over the bare `telemetry` contract, with a loopback node exporter per host (`node-exporter`) and every destination derived from the store's catalog entry. The local metrics pipeline converts delta streams to cumulative after identity enrichment, because the metrics remote-write destination translates only cumulative streams; a producer that exports OTLP to its own host's loopback endpoint — every Pi process does — is converted before its export, so the gateway's ingress needs no such processor (D-089). Every host's telemetry carries the canonical host ID — OTLP `host.name`, the scrape host label and journal `host_name` all resolve to the identifier the fleet inventory, deploy metadata and web policy use, while the environment label stays unset because the fleet has no environment dimension — and unit state and the Tailscale daemon's metrics reach the store through values of nix-fleet's contract this repository selects rather than states (D-085). `home-forge` is the OTLP gateway; general and AI routes both deliver traces, metrics and logs to the operational stores, while only the AI route adds Langfuse and Latitude for traces. The AI route carries fixed resource provenance `telemetry.route="ai"`; the marker is neither classification nor admission control. OTLP logs are default-deny on both routes, retaining only the specified resource identity fields and the AI route marker; record attributes are dropped except derived `trace_flags`, and scope attributes are dropped. Body, severity and trace/span IDs remain; VictoriaLogs stores event time as `_time`, with observed time as fallback rather than storing both separately (D-083, D-086). Trace output views shape the AI receiver per destination: VictoriaTraces receives no prompt, completion or tool payload, while Latitude's leg bridges the deployed image's legacy message format (D-084).

**Caching:** Nix store optimization via `auto-optimise-store = true`. Substituters come from nix-fleet's `nix-baseline`: `cache.nixos.org`, nix-community cachix, `cache.numtide.com`, and the fleet's sovereign niks3 cache (`cache.shrublab.xyz`), where CI and hosts publish. The CI build plane is the fleet's own machines, reached through nix-fleet's build-account and `ci` profile (D-082). Write access to the cache API is federated to CI with GitHub OIDC, and each calling repository's identity reserves its own pin namespace (`<repository>-main-<system>`) so a token minted for one repository cannot move another repository's `main` pin (D-099). The server's `/metrics` endpoint is collected by the cache host's own vmagent and rendered as the `Niks3 cache` Grafana board, so cache size, request health and garbage collection are visible beside the rest of the fleet telemetry.

**Storage:** Mutable service state on `/srv/data/<service>` mount (ext4, labeled `srv-data`). Heavy-app bulk storage on `/srv/storage` (ext4, labeled `srv-storage`, on `oci-melb-1` and `home-forge`; repurposed from `oci-melb-1`'s retired media mount, D-070). Nix store on separate `/nix` partition on split-disk layouts. Disk layouts are host-local disko files beside their host. Backup via restic to per-host Cloudflare R2 buckets.

**Published provenance:** each host carries its own configuration at `/etc/nixos-source` (`modules/flake/provenance.nix`, `environment.etc."nixos-source".source = self.outPath`). Local evaluation uses the Git-tree form `.#`, so that copy is the tracked configuration set (~5.5 MB) rather than the raw working directory (440 MB, including VCS metadata, `.terraform` provider binaries, editor caches, and plaintext credential files), and `system.configurationRevision` is populated (`self.rev`/`self.dirtyRev`) instead of `null`. The Git index is therefore a precondition: `tests/check-flake-source-tracking.sh` fails when a jj-tracked file is missing from it, and index-mutating Git commands are not used in this colocated repository (D-057).

**Secrets:** All secrets encrypted with `sops` + `age`. Decrypted at activation time by `sops-nix`. Path-scoped `.sops.yaml` rules enforce blast-radius boundaries. No plaintext secrets in git.

**CI/CD:** GitHub Actions is the hosted surface; the build plane is the fleet's own machines — the hand-dispatched `fleet-build` workflow calls nix-fleet's `build-push-cache` workflow to build `.#checks` for both architectures on the fleet's builders, publishing to the niks3 cache, while routine validation in `ci.yml` builds no fleet output. Tailscale `tailscale/github-action@v4` for tailnet access. Serial deploy ordering: `la-admin-1` → `oci-melb-1`, each host verifying its profile is substitutable before activating (D-082).

**Identity:** Kanidm-based OIDC provides single-sign-on for admin services. Kanidm is self-hosted on `la-admin-1`. OIDC client configurations are generated from `policy/identity.json`. Host-level SSH auth integrates with Kanidm groups.

**Notifications:** All hosts run the notification daemon, deployed by the `notify` foundation aspect, which consumes nix-fleet's shared `notify` mechanism and binds only this fleet's policy. Deploy outcomes, beets runner failures, and registered systemd unit outcomes dispatch via the daemon; registration is `services.notify.events.<unit>`, written by the capability that owns the unit. The `notify` CLI provides a stdin-pipe interface for any script to send notifications. The daemon, the CLI and the event handler are nix-fleet's now (they hold no fleet identity, topic, or route literal); publisher membership, ntfy topic ACLs, and the ntfy auth-file binding are homelab policy and encrypted secrets — they stay in this repository (`modules/notifications/push-server.nix` policy, `modules/notifications/notify.nix` conventions, `secrets/services/ntfy*.yaml` readership).
