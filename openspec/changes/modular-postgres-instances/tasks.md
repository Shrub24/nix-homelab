## 2. Mechanism leaf

- [x] 2.1 Create the mechanism under `modules/services/postgres/`: `instances.<name>.{runtime, port, dataDir, version}` and the consumer registry `consumers.<instance>.<consumer>.{database, role, auth, allowedCIDRs, secretFile, secretKey}`, with rendering for SQL provisioning and `pg_hba` derived from the registry instead of per-consumer option blocks. Implemented as `modules/services/postgres.nix` (namespace `services.postgres`, D-058): instances carry `port` and `dataDir` only — `runtime` and `version` were deliberately dropped per the supervisor narrowing (containers are a later runtime decision) — and the registry carries `database`/`role`/`auth`/`passwordKey`/`allowedCIDRs`, with `secretFile` a mechanism-level option because every provider-side role password lives in one file today.
- [x] 2.2 Carry the existing responsibilities across unchanged: data directory ownership/tmpfiles, `postStart` provisioning, `postgresqlBackup` export feeding the restic job, and the `ReadWritePaths`/service-config hardening.
- [x] 2.3 Add the named fail-closed errors (MPI-3) and verify each fires on a mutated copy: unknown instance, consumer without a credential path when its auth mode needs one, and port drift against the instance's real listen port.
- [x] 2.4 Support consumer-required extensions and host-overridable sizing (needed by the `degoog-hindsight-home-forge` change's pgvector requirement): a consumer declares `extensions` (SQL names created with `IF NOT EXISTS` in its database at startup) and the instance declares `packages` (the extension packages the server is built with); mechanism tuning values are `lib.mkDefault` so a host overrides them without force. - [x] 2.5 Instance facts move to the host: the `postgres` aspect supplies enablement only, and the host's `_nixos.nix` declares `instances.<name>.{port, dataDir}` — two clusters may then carry distinct names without a key collision in the contract family, and no host-name literal enters the aspect.

## 6. Contract refinements and the AudioMuse migration (operator-directed)

- [x] 6.1 Make the consumer registration the single source for its credential: `password = { file, key }` replaces the provider-side `secretFile` plus per-consumer `passwordKey`, so the provider reads the same file and key the consumer authenticates with; the top-level secret file option is gone and a missing file fails with a named error.

- [x] 6.6 Write `docs/runbooks/postgres-consumer-migration.md`: same-host versus cross-host moves, the dump/restore sequence with extension checks and verification steps, and what backup coverage looks like afterwards.
- [x] 6.7 Fire-verify the new named errors on scratch copies: scram without a credential, a credential file that does not exist, and two instances on one host.
- [x] 6.8 Fix the fresh-cluster failure found on the first home-forge deploy: nixpkgs creates databases and roles in `postgresql-setup.service`, which runs *after* `postgresql.service`, so consumer credentials and setup SQL cannot live in `postStart` (the role does not exist yet; psql exited 3, `ExecStartPost` failed, the unit hit `start-limit-hit` and deploy-rs rolled back). Provisioning is now `postgresql-provision.service` (oneshot, `User=postgres`), ordered `after`/`requires` `postgresql-setup.service` and wired to `postgresql.target` the way nixpkgs wires its own units; a missing role fails with a named message; credentials rotate by restarting that unit instead of the database; the client is the cluster's own server package rather than nixpkgs' default major; and the scaffold contract ratchets the ordering and the empty `postStart`. The pre-existing module only worked because OCI's cluster had held the role for generations.
